# Route reference

Is your resource emulated? This page answers it without installing anything.

Everything below is written by the binary that serves it: `feint docs` mounts the
packs in process and prints what they registered, so this page cannot claim a
route the emulator does not answer, nor miss one it does. Regenerate it with
`mise run docs:coverage`, and the CI fails if it is stale.

Two things it does not tell you, on purpose:

- **How much of the upstream API that represents.** That is the coverage table in
  the [README](../README.md#coverage), which counts upstream *operations* from
  the SDK scan rather than routes.
- **What a route does with what it receives.** A mounted route is a protocol
  promise, not a behavioural one. `docs/limits.md` records where the two differ.

What it does tell you, beside each route, is what the last recorded conformance
run proved about it — and, in the table below, how much of each pack that adds
up to.

What each axis says, one line each. They are independent and are never added
into one number: none of them implies another, and an operation can be driven
by a real client and never contract-checked, or probed and never driven.

| Axis | What earns it |
|---|---|
| `driven` | a real client reached it in the recorded run; it proves what the suite asserted, nothing more |
| `probed` | the contract-driven probe validated an answer here against the operation's own schema, a success (`response`) or a refusal (`refusal`) |
| `contract` | at least one answer was validated against the provider's own API description and none violated it (`unchecked`: none was ever validated, which is not the same as no violation) |
| `dataplane` | it was driven in a run whose machines were real, so the control plane ran with its side effects on |
| `shape` | a recorded real-cloud answer covers it, from `shapes/` — which `mise run shapes:fold` also fills from the committed corpora; it says the answer has been held against a real one, not that the offline gate re-issues the call |
| `behaviour` | it took part in a create-to-destroy sequence the emulator's own store observed, inside a span a suite declared |
| `negative` | it really answered 4xx to a real client inside a span where a suite demanded a refusal; **an injected fault never earns it**, so arming faults cannot move this number |

**An injected fault earns none of them.** The emulator can be made to refuse on
purpose (`PUT /_feint/faults`), and an answer produced that way moves no counter
here: the operation stays un-driven and un-proven, and a `negative` span cannot
be closed on it. So the 17 % and the 97 % at the two ends of that column are
refusals real clients really got, and no amount of arming faults can raise them.

A percentage here is of the operations this emulator *serves*, never of the
provider's whole API — that comparison is the coverage table in the
[README](../README.md#coverage), which counts the upstream surface. And one
column used to move on its own: `behaviour` attributed a store touch only while
a single client request was in flight, so two identical runs marked the same
number of operations and not the same ones. It reads the goroutine that made
the touch now — two runs with machines off produce an identical record, and a
span that still cannot attribute a touch says how many it lost (#398).

## Every route

<!-- routes:start -->
<!-- Generated by `mise run docs:coverage`. Do not edit by hand. -->

378 routes across 3 packs. Every route names the upstream operation it
stands for, in the provider's own spelling: that name is what the drift scan
matches against the upstream SDK, so a route that renames it stops being
counted.

Each route lists the proofs it has earned — independent axes, side by side,
never added into one number. None implies another: a route can be driven by
a real client and never contract-checked, probed and never driven. The order
of tokens is fixed for diff stability; it is not a ranking.

- `client` — a real client drove it in the recorded conformance run. It
  proves what the suite asserted, nothing more: #116 and #83 were driven the
  whole time they were wrong.
- `contract` — at least one answer was validated against the provider's own
  API description and none violated it. `contract-violated` — one did.
  Absent: no answer of this operation was ever validated, which is a
  different fact from "no violation".
- `shape` — an observed real-cloud answer covers it, and the shapes gate
  holds the emulator to that record, field by field.
- `runtime` — it was driven in a run whose machines were real (machines: incus, none).
  It says the control plane ran with side effects on; it does not say a
  machine-level assertion named this operation.
- `probe` — the contract-driven probe built a call from the operation's own
  request schema and its success answer validated against the response
  schema; where the contract declares a page-size parameter, one probed
  call carried it and the answer stayed within the bound it asked. Its
  refusals, when it met any, validated against the provider's declared
  error shape. Protocol only: a well-shaped empty inventory would pass,
  and cursors and filters are not exercised.
- `probe-refusal` — everything the probe could validate here was a refusal,
  read and validated against the provider's declared error shape. It does
  not say the success shape was ever seen. Absent (neither token): the
  probe validated nothing — not reached, or answers nothing upstream
  gives a shape to.
- `behaviour` — inside a span a suite declared to be a lifecycle assertion,
  this operation touched a resource the emulator's own store saw created and
  then destroyed. The suite declares the span; the emulator verifies the
  lifecycle and resolves which operations took part — no operation is ever
  named by hand. It does not say the operation's own effect was asserted,
  only that it worked inside a real create-to-destroy sequence.
- `negative` — inside a span where a suite declared it was demanding a
  refusal, this operation really answered a 4xx to a real client, and the
  emulator refuses to close such a span when no refusal happened. One
  demanded refusal earns it; it does not say every refusal the operation
  owes was reproduced.

The two span-borne axes were absent until the suites could emit a signal at
the assertion level (`POST /_feint/assert`): a hand-written value would have
been a comment, not a control.

**An injected fault earns none of these.** The emulator can be made to refuse
on purpose (`PUT /_feint/faults`), and an answer produced that way moves no
counter here: the operation stays un-driven, un-checked and un-proven, and a
`negative` span cannot be closed on it. An operation whose only refusal came
from a rule somebody armed has not been proven, it has been staged — so the
injected answers are counted apart, under `injected` on
`/_feint/conformance`, and `tools/conformance/score.sh` refuses a run that
carries any.

The record is `coverage/evidence.json`, regenerated by `mise run
evidence:update`: a proof disappears from these rows when its assertion
disappears from the suite.
